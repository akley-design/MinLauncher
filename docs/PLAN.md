# MinLauncher — план разработки

Лаунчер Minecraft, совместимый с TLauncher, но запускающийся минимум на **20 % быстрее**
и оптимизирующий саму игру.

> Статус документа: Phase 0 закрыт, Phase 1, Phase 2, Phase 3 (оболочка
> на стороне Rust и интерфейс) и Phase 5 (каркас измерителя) в работе.
> Реализованы `ml-core`, `ml-storage`, `ml-minecraft`, `ml-launch`,
> `ml-bench`, `ml-desktop` и `apps/ui`; `apps/java` — каркас.
> Один агент, последовательная работа.

---

## 1. Цели и метрики

Главное требование — измеримое. «На 20 % быстрее» без определения точки замера
невозможно проверить, поэтому метрики зафиксированы заранее.

| ID | Метрика | Что замеряется | Цель |
|----|---------|----------------|------|
| **M1** | `launcher_cold_start` | От запуска процесса до готового окна (холодный старт, первый запуск, кэш пуст) | ≤ 80 % от TLauncher |
| **M2** | `launcher_warm_start` | То же, но с прогретым кэшем | ≤ 80 % от TLauncher |
| **M3** | `click_to_window` | Клик по кнопке «Играть» → окно игры | **≤ 80 % от TLauncher** (основная метрика) |
| **M4** | `fresh_install` | Полная установка версии 26.3 с нуля | ≤ 80 % от TLauncher |
| **M5** | `in_game_fps` | Средний FPS и 1 % low в основном билде | ≥ 110 % от TLauncher |
| **M6** | `in_game_frametime` | 99-й перцентиль времени кадра (1 % low) | ≤ 90 % от TLauncher |
| **M7** | `launcher_rss` | Потребление памяти процессом лаунчера | ≤ 60 МБ |
| **M8** | `game_rss` | Потребление памяти процессом игры | ≤ 90 % от TLauncher |

**M3 — целевая метрика.** Именно её имеет в виду пользователь, когда говорит
«запускается быстрее»: нажал кнопку — увидел игру. M1/M2 ограничивают
время запуска самого приложения, M5/M6 — «сама игра оптимизирована в разы».

### Как измеряется

- Лаунчер пишет разметку времени (`Instant` → `tracing`) в каждой фазе старта.
  Метки видны и в логах, и в UI (вкладка «Производительность»).
- Игровые метрики собирает Java-агент (`apps/java/agent`): он меряет время
  до первой отрисовки кадра, стабильность FPS и 1 % low, и выгружает их
  в лаунчер через локальный IPC.
- Каждый замер — серия из N=30 прогонов; в базу пишутся p50/p95/p99/mean/stddev.
  Одиночный замер — не результат.
- Сравнение с TLauncher выполняется на одной и той же машине, в одном сеансе,
  с одинаковыми версиями игры и Java. Конфигурация фиксируется в метаданных
  замера (`meta_json`).

## 2. Архитектура

```
┌──────────────────────────────────────────────────────────────┐
│  apps/ui — React 19 + TypeScript + Vite                      │
│  zustand (состояние UI) + TanStack Query (данные) + Router   │
└──────────────────────────┬───────────────────────────────────┘
                           │ Tauri IPC (команды + события)
┌──────────────────────────▼───────────────────────────────────┐
│  crates/ml-desktop — Tauri 2 оболочка                         │
│  state, команды, плагины, трей, автообновление               │
└───┬────────────┬──────────────┬──────────────┬──────────────┘
    │            │              │              │
┌───▼────┐  ┌────▼─────┐  ┌─────▼──────┐  ┌────▼─────┐
│ml-core │  │ml-storage│  │ml-minecraft │  │ml-launch │
│ домен  │  │SQLite/JSON│  │метаданные, │  │JVM,      │
│ типы   │  │          │  │загрузки,   │  │аргументы,│
│ правила│  │          │  │ассеты, JRE │  │процесс   │
└────────┘  └──────────┘  └────────────┘  └────┬─────┘
                                                │
       ┌────────────────────────────────────────┘
┌──────▼──────────────────────────────────────────────┐
│ apps/java — оптимизация самой игры                    │
│  agent/  Java-агент: тайминги старта, метрики FPS     │
│  mod/    Fabric-мод: миксины, настройки рендера        │
└───────────────────────────────────────────────────────┘
```

`ml-bench` — отдельный крейт с бенчмарками (criterion) и сохранением результатов
в БД; пишет и читает те же таблицы `benchmarks`, что и UI.

### Почему так

- **`ml-core` без зависимостей и без I/O.** Общий словарь предметной области.
  Правила Mojang, версии, аккаунты, пути, конфиг. Чем легче crate, тем дешевле
  он пересобирается — а `ml-core` переиспользуется всеми остальными.
- **SQLite, а не sqlx.** `sqlx` 0.9 требует Rust 1.94, `rusqlite` 0.40 работает
  на 1.90. Синхронный API + `r2d2` проще в использовании и дешевле по
  зависимостям; собранный SQLite не требует системной библиотеки.
- **Токены — не в базе.** Access/refresh токены лежат в отдельном файле
  `secrets.json`. Дамп базы (для баг-репорта, бэкапа) не утекает учётными
  данными. Это разделение зафиксировано в `ml-storage`.
- **Правила Mojang — один evaluator.** `ml-core::rules` используется и для
  выбора библиотек, и для фильтрации JVM-аргументов, поэтому две части
  не могут разойтись в том, что значит «эта платформа».

Данные Mojang сверены напрямую с piston-meta/piston-data:

- В `arguments.jvm` поле `value` — **иногда массив, иногда строка**. Это ловушка

  Таблица зафиксирована в тесте `fallback_matches_observed_manifests`.

### Проверено по фактам: как устроены нативы

Схема нативов в Mojang менялась трижды, и лаунчер обязан понимать все три:

1. **Старая форма** (до 1.19): у библиотеки есть `downloads.classifiers` с
   ключом `natives-windows` / `natives-linux` / `natives-osx`.
2. **Новая форма** (1.19+): нативы лежат в **классификаторе Maven-координаты**
   — `org.lwjgl:lwjgl:3.4.3:natives-windows`. У 26.3 в `downloads.classifiers`
   пусто, а нативы есть только в координате.
3. **Вариант по архитектуре** (3.4.x): `natives-windows` и
   `natives-windows-arm64` — **два разных jar-а**, в одном лежит
   `windows/x64/…`, в другом `windows/arm64/…`. Правила версии смотрят
   только на систему, поэтому на Windows разрешаются оба, и распаковывать
   надо оба: они не конфликтуют, потому что лежат в разных каталогах.

Распаковка в modern-версии идёт в **четыре подкаталога**:
`java/` (`java.library.path`), `jna/` (`jna.tmpdir`),
`lwjgl/` (`org.lwjgl.system.SharedLibraryExtractPath`),
`netty/` (`io.netty.native.workdir`). Старые версии указывают все четыре
свойства на саму папку нативов. Лаунчер читает эти свойства **из аргументов
версии**, а не угадывает по номеру версии, поэтому обе раскладки работают
без ветвления.

Проверено на живых данных 26.3: **74 библиотеки** из 114 применимы на
Windows x86-64, из них **21** несут нативы (20 LWJGL + 1 jtracy). Число 74
посчитано дважды — Rust-резолвером и отдельным скриптом на Python, — результаты
совпали. Нативы лежат в корне jar-а (`jtracy-jni-windows.dll` — через
`java.library.path`; `windows/x64/org/lwjgl/lwjgl.dll` — LWJGL распаковывает
сам из classpath).

## 5. Ограничения окружения (надо решить)

1. **Нет Windows SDK.** `C:\Program Files (x86)\Windows Kits\10` пуст, MSVC-хост
   не может линковать (`kernel32.lib` отсутствует). Сейчас сборка идёт
   GNU-тулчейном (`stable-x86_64-pc-windows-gnu`), закреплённым в
   `rust-toolchain.toml`.
   *Почему так:* build-скрипты и proc-макросы всегда собираются под **хост**,
   а `--target` на это не влияет. GNU-тулчейн самодостаточен — нужен только
   mingw-w64 gcc.
   *Что сделать:* для релизной сборки Tauri лучше MSVC — нужен Windows SDK
   (~1–2 ГБ, с правами администратора). Тогда меняется одна строка в
   `rust-toolchain.toml`.
2. **MSYS2 `ld.exe` не понимает не-ASCII пути.** Домашний каталог содержит
   кириллицу («Вася»), и линкер ломал путь до объектных файлов. Обойдено через
   `target-dir = "C:/Users/Public/minlaucher-target"` в `.cargo/config.toml`.
   C-компиляция при этом не затронута — ограничение только у `ld.exe`.

   *Точная причина (установлена экспериментально):* драйвер MinGW
   (`x86_64-w64-mingw32-gcc`) декодирует свою командную строку через
   **ANSI-кодовую страницу** Windows (на этой машине 1251), а Rust передаёт
   пути в **UTF-8**. Кириллица в этих кодировках не совпадает, поэтому
   драйвер ищет каталог, которого не существует. Проверено напрямую: одна и
   та же команда, отданная как ANSI-байты, линкуется, а та же как UTF-8 —
   падает с «cannot find -lwindows.0.53.0».

   *Что ещё пришлось починить:* путь до import-библиотеки
   (`libwindows.0.53.0.a`) лежит в реестре Cargo (`$CARGO_HOME`), то есть
   под `C:\Users\Вася\.cargo` — его нельзя перенести настройкой `target-dir`.
   Build-скрипт `ml-desktop` копирует библиотеку в `OUT_DIR` и добавляет
   этот каталог в путь линковки (`cargo:rustc-link-search`). Там же
   раскладывается иконка — `windres` страдает ровно от той же проблемы.

   *Альтернатива на будущее:* `rust-lld` из тулчейна Unicode-чист (он
   написан на Rust и ходит в файлы через wide-API), и линкует заметно
   быстрее GNU `ld`. Проверено: с `rust-lld` проблема с кириллицей
   исчезает полностью, но требуется самодостаточный MinGW-тулчейн Rust,
   в котором нет символа `nanosleep64` (нужен `aws-lc-sys`). Переход
   планируется вместе с установкой Windows SDK.

3. **Манифест Windows нужен каждому таргету крейта, а не только бинарнику.**
   Tauri собирает иконку, версию и манифест в один ресурс и отдаёт линковщику
   через `cargo:rustc-link-arg-bins` — то есть **только бинарникам** крейта.
   Тестовые бинарники в список не входят, и без манифеста они не стартуют
   вовсе.

   Причина — в самом манифесте: он просит Windows у загрузчика версию 6
   общих элементов управления (`Microsoft.Windows.Common-Controls` 6.0). Без
   него загрузчик берёт устаревшую `comctl32.dll` из `System32`, а код
   импортирует `TaskDialogIndirect` — функцию, которую экспортирует **только**
   версия 6. Экспорта нет, и процесс не стартует:
   `STATUS_ENTRYPOINT_NOT_FOUND` (0xC0000139), ещё до первого теста.

   *Что сделано:* Tauri вызывается с `new_without_app_manifest()`, а
   манифест собирается в `crates/ml-desktop/build.rs` отдельным ресурсом и
   линкуется в **каждый** таргет крейта — и в бинарник приложения, и в
   тестовые бинарники. Манифест один на весь крейт: иначе в бинарнике
   оказалось бы два ресурса `RT_MANIFEST`, и какой из них возьмёт
   загрузчик — непредсказуемо.

   *Побочная ошибка, найденная по пути:* путь в `.rc` нельзя писать
   обратными слэшами — компилятор ресурсов считает `\` управляющим
   символом и ищет файл с другим именем. Ошибка при этом молчащая, если
   не разбирать результат компиляции. Путь пишется прямыми слэшами, а
   `CompilationResult::Failed` обрабатывается явно.

   *Побочный эффект:* пока тестовый бинарник не мог стартовать, были
   незамеченными ещё два настоящих дефекта — `instance_id` собирал
   идентификатор из одних тире для кириллических названий
   (`is_ascii_alphanumeric` → `is_alphanumeric`), и тест флага сборщика
   мусора утверждал неверное ожидание. Оба исправлены.

## 6. Риски

| Риск | Влияние | Что делаем |
|------|---------|-----------|
| Windows SDK не установят | Релизная сборка Tauri невозможна | Документировано; GNU-хост работает для разработки и CI |
| «Быстрее на 20 %» не подтвердится на чужой машине | Спор о результате | Фиксируем протокол замера: N=30, одинаковый билд, метаданные в БД |
| Мод-часть ломает совместимость | Игра не запускается у части пользователей | Мод всегда выключаемый; агент — единственная часть, включённая по умолчанию |
| Смена схемы БД у пользователя | Потеря состояния | Миграции только вперёд, с записью в `schema_migrations`; тест на повторное открытие |
| Ассеты ~460 МБ на версию | Долгая первая установка | Контент-адресуемое хранилище: объекты делятся между версиями |
| Манифест Common-Controls v6 не попал в таргет | Тесты не стартуют (0xC0000139) | Манифест линкуется в каждый таргет крейта из `build.rs`; Tauri оставлен без своего |

## 7. Порядок работ

1. `ml-minecraft`: манифест → version JSON → библиотеки → ассеты → JRE. *(Phase 1 — в работе)*
2. `ml-launch`: JVM → аргументы → процесс. *(Phase 2 — в работе)*
3. `ml-bench`: сценарии замера и протокол сравнения с TLauncher. *(Phase 5 — каркас готов)*
4. `ml-desktop` + `apps/ui`: команды, события, окно. *(Phase 3 — готов)*
5. `apps/java`: агент → мод. *(Phase 4)*

Каждый крейт завершается зелёным `cargo test` + `cargo clippy` (pedantic) +
`cargo fmt --check`; фронтенд — зелёным `tsc --noEmit` + `eslint .` +
`prettier --check .` + `vitest run`. CI прогоняет то же самое.
