# MinLauncher — план разработки

Лаунчер Minecraft, совместимый с эталонным лаунчером по расположению файлов,
но запускающийся минимум на **20 % быстрее** и оптимизирующий саму игру.

> Статус документа: Phase 0 закрыт, Phase 1, Phase 2, Phase 3 (оболочка
> на стороне Rust и интерфейс), Phase 4 (агент и мод, проверены на живой
> игре) и Phase 5 (каркас измерителя) в работе.
> Реализованы `ml-core`, `ml-storage`, `ml-minecraft`, `ml-launch`,
> `ml-bench`, `ml-desktop`, `apps/ui` и `apps/java`.
> Один агент, последовательная работа.
>
> Тестов: **395** на Rust, **23** у агента, **18** у мода, **46** во
> фронтенде — 482 всего. Плюс сквозные тесты против настоящей игры и
> настоящих серверов Mojang.

## 1. Цели и метрики

Главное требование — измеримое. «На 20 % быстрее» без определения точки замера
невозможно проверить, поэтому метрики зафиксированы заранее.

| ID | Метрика | Что замеряется | Цель |
|----|---------|----------------|------|
| **M1** | `launcher_cold_start` | От запуска процесса до готового окна (холодный старт, первый запуск, кэш пуст) | ≤ 80 % от эталона |
| **M2** | `launcher_warm_start` | То же, но с прогретым кэшем | ≤ 80 % от эталона |
| **M3** | `click_to_window` | Клик по кнопке «Играть» → окно игры | **≤ 80 % от эталона** (основная метрика) |
| **M4** | `fresh_install` | Полная установка версии 26.3 с нуля | ≤ 80 % от эталона |
| **M5** | `in_game_fps` | Средний FPS и 1 % low в основном билде | ≥ 110 % от эталона |
| **M6** | `in_game_frametime` | 99-й перцентиль времени кадра (1 % low) | ≤ 90 % от эталона |
| **M7** | `launcher_rss` | Потребление памяти процессом лаунчера | ≤ 60 МБ |
| **M8** | `game_rss` | Потребление памяти процессом игры | ≤ 90 % от эталона |

**M3 — целевая метрика.** Именно её имеет в виду пользователь, когда говорит
«запускается быстрее»: нажал кнопку — увидел игру. M1/M2 ограничивают
время запуска самого приложения, M5/M6 — «сама игра оптимизирована в разы».

### Как измеряется

- Лаунчер пишет разметку времени (`Instant` → `tracing`) в каждой фазе старта.
  Метки видны и в логах, и в UI (вкладка «Производительность»).
- Игровые метрики собирает Java-агент (`apps/java/agent`): он меряет время
  до первой отрисовки кадра, стабильность FPS и 1 % low, и выгружает их
  в лаунчер через локальный IPC.
- Каждый замер — серия из N=30 прогонов; в базу пишутся p50/p95/p99/mean/stddev.
  Одиночный замер — не результат.
- Сравнение с эталонным лаунчером выполняется на одной и той же машине, в одном сеансе,
  с одинаковыми версиями игры и Java. Конфигурация фиксируется в метаданных
  замера (`meta_json`).
- **Эталон** — вторая сторона сравнения. Его замеры приходят внешним файлом,
  снятым по тому же протоколу; установку эталона лаунчер не трогает.

## 2. Архитектура

```
┌──────────────────────────────────────────────────────────────┐
│  apps/ui — React 19 + TypeScript + Vite                      │
│  zustand (состояние UI) + TanStack Query (данные) + Router   │
└──────────────────────────┬───────────────────────────────────┘
                           │ Tauri IPC (команды + события)
┌──────────────────────────▼───────────────────────────────────┐
│  crates/ml-desktop — Tauri 2 оболочка                         │
│  state, команды, плагины, трей, автообновление               │
└───┬────────────┬──────────────┬──────────────┬──────────────┘
    │            │              │              │
┌───▼────┐  ┌────▼─────┐  ┌─────▼──────┐  ┌────▼─────┐
│ml-core │  │ml-storage│  │ml-minecraft │  │ml-launch │
│ домен  │  │SQLite/JSON│  │метаданные, │  │JVM,      │
│ типы   │  │          │  │загрузки,   │  │аргументы,│
│ правила│  │          │  │ассеты, JRE │  │процесс   │
└────────┘  └──────────┘  └────────────┘  └────┬─────┘
                                                │
       ┌────────────────────────────────────────┘
┌──────▼──────────────────────────────────────────────┐
│ apps/java — оптимизация самой игры                    │
│  agent/  Java-агент: тайминги старта, метрики FPS     │
│  mod/    Fabric-мод: миксины, настройки рендера        │
└───────────────────────────────────────────────────────┘
```

`ml-bench` — отдельный крейт с бенчмарками (criterion) и сохранением результатов
в БД; пишет и читает те же таблицы `benchmarks`, что и UI.

### Почему так

- **`ml-core` без зависимостей и без I/O.** Общий словарь предметной области.
  Правила Mojang, версии, аккаунты, пути, конфиг. Чем легче crate, тем дешевле
  он пересобирается — а `ml-core` переиспользуется всеми остальными.
- **SQLite, а не sqlx.** `sqlx` 0.9 требует Rust 1.94, `rusqlite` 0.40 работает
  на 1.90. Синхронный API + `r2d2` проще в использовании и дешевле по
  зависимостям; собранный SQLite не требует системной библиотеки.
- **Токены — не в базе.** Access/refresh токены лежат в отдельном файле
  `secrets.json`. Дамп базы (для баг-репорта, бэкапа) не утекает учётными
  данными. Это разделение зафиксировано в `ml-storage`.
- **Правила Mojang — один evaluator.** `ml-core::rules` используется и для
  выбора библиотек, и для фильтрации JVM-аргументов, поэтому две части
  не могут разойтись в том, что значит «эта платформа».

### Проверено по фактам (октябрь 2026)

Данные Mojang сверены напрямую с piston-meta/piston-data:

- Актуальный релиз — **26.3**, снапшот — `26.4-snapshot-4`; всего 919 версий.
- **26.3 требует Java 25** (`java-runtime-epsilon`, v25.0.1), 114 библиотек,
  5147 ассет-объектов (462,4 МБ).
- В `arguments.jvm` поле `value` — **иногда массив, иногда строка**. Это ловушка
  совместимости для старых лаунчеров; учтена в дизайне `ml-minecraft`.
- Современные version JSON используют только правила `os`/`arch`, без `version`.
- Соответствие JRE: ≤1.16.5 → `jre-legacy` (8), 1.17 → `alpha` (16),
  1.18 → `beta`/`gamma` (17), 1.20.5…1.21.11 → `delta` (21), 26.1+ → `epsilon` (25).
  Таблица зафиксирована в тесте `fallback_matches_observed_manifests`.

### Проверено по фактам: как устроены нативы

Схема нативов в Mojang менялась трижды, и лаунчер обязан понимать все три:

1. **Старая форма** (до 1.19): у библиотеки есть `downloads.classifiers` с
   ключом `natives-windows` / `natives-linux` / `natives-osx`.
2. **Новая форма** (1.19+): нативы лежат в **классификаторе Maven-координаты**
   — `org.lwjgl:lwjgl:3.4.3:natives-windows`. У 26.3 в `downloads.classifiers`
   пусто, а нативы есть только в координате.
3. **Вариант по архитектуре** (3.4.x): `natives-windows` и
   `natives-windows-arm64` — **два разных jar-а**, в одном лежит
   `windows/x64/…`, в другом `windows/arm64/…`. Правила версии смотрят
   только на систему, поэтому на Windows разрешаются оба, и распаковывать
   надо оба: они не конфликтуют, потому что лежат в разных каталогах.

Распаковка в modern-версии идёт в **четыре подкаталога**:
`java/` (`java.library.path`), `jna/` (`jna.tmpdir`),
`lwjgl/` (`org.lwjgl.system.SharedLibraryExtractPath`),
`netty/` (`io.netty.native.workdir`). Старые версии указывают все четыре
свойства на саму папку нативов. Лаунчер читает эти свойства **из аргументов
версии**, а не угадывает по номеру версии, поэтому обе раскладки работают
без ветвления.

Проверено на живых данных 26.3: **74 библиотеки** из 114 применимы на
Windows x86-64, из них **21** несут нативы (20 LWJGL + 1 jtracy). Число 74
посчитано дважды — Rust-резолвером и отдельным скриптом на Python, — результаты
совпали. Нативы лежат в корне jar-а (`jtracy-jni-windows.dll` — через
`java.library.path`; `windows/x64/org/lwjgl/lwjgl.dll` — LWJGL распаковывает
сам из classpath).

## 4. Фазы

### Phase 0 — Фундамент *(в работе)*
`ml-core`, `ml-storage`, схема БД, окружение сборки, план. Готово: 97 тестов.

### Phase 1 — Метаданные и загрузки (`ml-minecraft`) *(в работе)*
- ✅ Клиент манифеста версий с кэшем и ETag.
- ✅ Разбор version JSON: правила, аргументы (с учётом array-or-string), класс точки входа.
- ✅ Резолвинг библиотек по правилам → таблица `libraries`.
- ✅ Движок загрузок: параллельность (16 одновременно), ретраи с backoff,
  проверка SHA-1, отчёт о ходе через колбэк. **Здесь живёт основная часть
  выигрыша в M4** — эталонный лаунчер скачивает ассеты последовательно и часто
  перекачивает.
- ✅ Докачка: `Range: bytes=N-` с запроса, 206 дописывает `.part`, 200
  перекачивает с нуля, 416 выбрасывает слишком длинный остаток. Хеш
  засевается байтами, что уже на диске, иначе собранный файл никогда
  не сошёлся бы.
- ✅ Очередь загрузок в БД: план установки записывается пачкой одной
  транзакцией, после батча состояния доводятся до `Completed` с размером
  файла на диске или `Failed` с причиной. *(Экрана очереди пока нет — есть
  только команда `list_downloads`.)*
- ✅ Менеджер JRE: манифест `java-runtime-*`, скачивание, распаковка.
  Рантайм — не архив: манифест перечисляет каждый его файл отдельно, и
  каждый качается сам по себе. Путь из манифеста — это чужие данные,
  поэтому он проверяется до присоединения: манифест не может записать
  файл за пределы каталога рантайма. *(Вариант LZMA не распаковывается —
  у каждого опубликованного файла есть и обычная загрузка.)*
- ✅ Контент-адресуемое хранилище ассетов: объект скачивается один раз на все
  версии, имя файла — это SHA-1 его содержимого.

#### Как устроена установка

Команда `install_version` идёт по шагам, и каждый шаг — это то, что
уже умеет `ml-minecraft`:

1. **Документ версии** — из кэша `version_manifest_v2.json`, а если его нет,
   из сети. Дальше он кладётся в `versions/<id>/version.json` — ровно туда,
   куда его потом ищет лаунчер.
2. **Индекс ассетов** — `assets.json` рядом с документом версии, и второй
   раз — `assets/indexes/<id>.json`, где id взят из документа версии. Второе
   место нужно **игре**: она читает индекс именно оттуда (это видно по
   байткоду `IndexedAssetSource` в 1.21.4), а лаунчеру оно не нужно.
3. **План** — `install::plan` считает, каких файлов не хватает: клиентский
   jar, библиотеки, ассеты. План перечисляет **только недостающее**, поэтому
   повторная установка почти ничего не качает.
4. **Загрузка** — движок качает 16 файлов одновременно, проверяет SHA-1,
   повторяет неудачные с backoff. Отчёт о ходе идёт через колбэк.

Отчёт о ходе поднимается вверх через **дроссель**: команда шлёт событие в
фронтенд не чаще десяти раз в секунду. Без дросселя на 4000 ассетов
фронтенд получил бы 4000 событий — и прокручивал бы список вхолостую.

#### Сквозной тест против настоящих серверов

`crates/ml-desktop/tests/install_end_to_end.rs` ставит настоящую 1.21.4
с серверов Mojang: скачивает клиентский jar, библиотеки и все ассеты, и
проверяет, что на диске лежит раскладка, которую потом ждёт лаунчер.
Тест не идёт сам по себе — включается `MINLAUNCHER_E2E=1`.

У него **свой каталог**, отдельный от других сквозных тестов. Это не
придирка: план установки перечисляет только недостающие файлы, поэтому
тест, который делит каталог с другим тестом, не видит в плане клиентский
jar и падает — хотя код исправен. Тест чистит каталог версии и хранилище
ассетов перед стартом, чтобы проверять установку «с нуля», и выполняется
один раз на весь бинарник, так что порядок тестов не важен.

`crates/ml-desktop/tests/runtime_end_to_end.rs` качает настоящий рантайм
Mojang (`java-runtime-delta`, 402 файла) и проверяет, что лаунчер находит
Java, которую сам только что положил на диск. У него свой каталог — третий,
отдельный от двух других.

Он нашёл баг, который ни один юнит-тест не мог найти: Java в системе была
новее рантайма, который публикует Mojang, и лаунчер брал её. Теперь
рантайм, скачанный лаунчером, идёт первым — документ версии игры называет
Java, с которой её тестировали, и новее не значит лучше.



### Phase 4 — Оптимизация игры (`apps/java`)

#### Две ошибки, которые нашлись только на живой игре

Обе нашлись при первом же запуске сквозного теста и обе невозможны в
юнит-тесте: они про то, как ведут себя чужие программы.

1. **Две копии ASM на classpath.** Игра 1.21.4 несёт `org.ow2.asm:asm:9.6`,
   загрузчик несёт `org.ow2.asm:asm:9.10.1`. Обе на classpath — и загрузчик
   отказывается стартовать: `LoaderUtil.verifyClasspath` перечисляет ресурсы
   `org/objectweb/asm/ClassReader.class` и падает, если их больше одного.
   *Правило:* библиотека загрузчика **заменяет** библиотеку игры с той же
   личностью (`group:artifact:classifier`), а не встаёт рядом. Загрузчик идёт
   первым в classpath, его версия новее — выигрывает она.
2. **Путь библиотеки строился из координаты, а не из документа.** Версия из
   двух кусков (`9.6`) читалась как версия `9` и расширение `6`, и jar оказывался
   по пути `org/ow2/asm/asm/9/asm-9.6` вместо `org/ow2/asm/asm/9.6/asm-9.6.jar`.
   Таких библиотек в 1.21.4 **восемь**. Теперь путь берётся из документа
   (`downloads.artifact.path`) — там он и есть у Mojang, — а координата
   остаётся запасным вариантом.

Отдельно: мод не использует Fabric API и больше не зависит от него, так что
лаунчеру не нужно его ставить.

#### Третья ошибка, которую нашёл только живой сервер

Она нашлась в сквозном тесте установки (`install_end_to_end.rs`) и стоила
больше всех остальных: **каждый ассет отдавался как 404**.

Хранилище ассетов адресовано по содержимому, и код брал адрес из хеша так:
двухбуквенный каталог и **остаток** хеша — `objects/ab/cdef…` и
`resources.download.minecraft.net/ab/cdef…`. На деле Mojang (и официальный
лаунчер) адресуют объект так: двухбуквенный каталог и **весь** хеш —
`objects/ab/abcdef…`, `resources.download.minecraft.net/ab/abcdef…`.

*Как это выглядело снаружи:* клиентский jar и библиотеки скачивались, а
затем установка **зависала** — 4039 ассетов, каждый с четырьмя попытками и
backoff, все четыре раза 404.

*Почему юнит-тест не мог это поймать:* URL собирался из хеша функцией, у
которой был тест — и тест проверял, что функция возвращает строку, которую
она же и собирает. Проверить, что эта строка ведёт на существующий файл, можно
только настоящим запросом.

*Как искали:* адрес ассета вынимался из настоящего индекса 1.21.4, и по
очереди перебирались хосты и формы пути. Ответ 404 на всех, кроме одного:
`/ab/abcdef…` — полный хеш. То же подтвердилось по исходникам PrismLauncher
(`getRelPath()` возвращает `hash.left(2) + "/" + hash`).

*Правило:* двухбуквенный каталог — это **способ разложить файлы по
директориям**, а не часть адреса. Имя файла — всегда весь хеш. Теперь так же
лежит и на диске, то есть хранилище совпадает с тем, что делает официальный
лаунчер, и читается чем угодно, что читает установку Mojang.

## 5. Ограничения окружения (надо решить)

1. **Нет Windows SDK.** `C:\Program Files (x86)\Windows Kits\10` пуст, MSVC-хост
   не может линковать (`kernel32.lib` отсутствует). Сейчас сборка идёт
   GNU-тулчейном (`stable-x86_64-pc-windows-gnu`), закреплённым в
   `rust-toolchain.toml`.
   *Почему так:* build-скрипты и proc-макросы всегда собираются под **хост**,
   а `--target` на это не влияет. GNU-тулчейн самодостаточен — нужен только
   mingw-w64 gcc.
   *Что сделать:* для релизной сборки Tauri лучше MSVC — нужен Windows SDK
   (~1–2 ГБ, с правами администратора). Тогда меняется одна строка в
   `rust-toolchain.toml`.
2. **MSYS2 `ld.exe` не понимает не-ASCII пути.** Домашний каталог содержит
   кириллицу («Вася»), и линкер ломал путь до объектных файлов. Обойдено через
   `target-dir = "C:/Users/Public/minlaucher-target"` в `.cargo/config.toml`.
   C-компиляция при этом не затронута — ограничение только у `ld.exe`.

   *Точная причина (установлена экспериментально):* драйвер MinGW
   (`x86_64-w64-mingw32-gcc`) декодирует свою командную строку через
   **ANSI-кодовую страницу** Windows (на этой машине 1251), а Rust передаёт
   пути в **UTF-8**. Кириллица в этих кодировках не совпадает, поэтому
   драйвер ищет каталог, которого не существует. Проверено напрямую: одна и
   та же команда, отданная как ANSI-байты, линкуется, а та же как UTF-8 —
   падает с «cannot find -lwindows.0.53.0».

   *Что ещё пришлось починить:* путь до import-библиотеки
   (`libwindows.0.53.0.a`) лежит в реестре Cargo (`$CARGO_HOME`), то есть
   под `C:\Users\Вася\.cargo` — его нельзя перенести настройкой `target-dir`.
   Build-скрипт `ml-desktop` копирует библиотеку в `OUT_DIR` и добавляет
   этот каталог в путь линковки (`cargo:rustc-link-search`). Там же
   раскладывается иконка — `windres` страдает ровно от той же проблемы.

   *Альтернатива на будущее:* `rust-lld` из тулчейна Unicode-чист (он
   написан на Rust и ходит в файлы через wide-API), и линкует заметно
   быстрее GNU `ld`. Проверено: с `rust-lld` проблема с кириллицей
   исчезает полностью, но требуется самодостаточный MinGW-тулчейн Rust,
   в котором нет символа `nanosleep64` (нужен `aws-lc-sys`). Переход
   планируется вместе с установкой Windows SDK.

3. **Манифест Windows нужен каждому таргету крейта, а не только бинарнику.**
   Tauri собирает иконку, версию и манифест в один ресурс и отдаёт линковщику
   через `cargo:rustc-link-arg-bins` — то есть **только бинарникам** крейта.
   Тестовые бинарники в список не входят, и без манифеста они не стартуют
   вовсе.

   Причина — в самом манифесте: он просит Windows у загрузчика версию 6
   общих элементов управления (`Microsoft.Windows.Common-Controls` 6.0). Без
   него загрузчик берёт устаревшую `comctl32.dll` из `System32`, а код
   импортирует `TaskDialogIndirect` — функцию, которую экспортирует **только**
   версия 6. Экспорта нет, и процесс не стартует:
   `STATUS_ENTRYPOINT_NOT_FOUND` (0xC0000139), ещё до первого теста.

   *Что сделано:* Tauri вызывается с `new_without_app_manifest()`, а
   манифест собирается в `crates/ml-desktop/build.rs` отдельным ресурсом и
   линкуется в **каждый** таргет крейта — и в бинарник приложения, и в
   тестовые бинарники. Манифест один на весь крейт: иначе в бинарнике
   оказалось бы два ресурса `RT_MANIFEST`, и какой из них возьмёт
   загрузчик — непредсказуемо.

   *Побочная ошибка, найденная по пути:* путь в `.rc` нельзя писать
   обратными слэшами — компилятор ресурсов считает `\` управляющим
   символом и ищет файл с другим именем. Ошибка при этом молчащая, если
   не разбирать результат компиляции. Путь пишется прямыми слэшами, а
   `CompilationResult::Failed` обрабатывается явно.

   *Побочный эффект:* пока тестовый бинарник не мог стартовать, были
   незамеченными ещё два настоящих дефекта — `instance_id` собирал
   идентификатор из одних тире для кириллических названий
   (`is_ascii_alphanumeric` → `is_alphanumeric`), и тест флага сборщика
   мусора утверждал неверное ожидание. Оба исправлены.

|------|---------|-----------|
| Windows SDK не установят | Релизная сборка Tauri невозможна | Документировано; GNU-хост работает для разработки и CI |

## 7. Порядок работ

1. `ml-minecraft`: манифест → version JSON → библиотеки → ассеты → JRE. *(Phase 1 — в работе)*
2. `ml-launch`: JVM → аргументы → процесс. *(Phase 2 — в работе)*
3. `ml-bench`: сценарии замера и протокол сравнения с эталоном. *(Phase 5 — каркас готов)*
4. `ml-desktop` + `apps/ui`: команды, события, окно. *(Phase 3 — готов)*
5. `apps/java`: агент → мод. *(Phase 4 — готов, проверено на живой игре)*

Каждый крейт завершается зелёным `cargo test` + `cargo clippy` (pedantic) +
`cargo fmt --check`; фронтенд — зелёным `tsc --noEmit` + `eslint .` +
`prettier --check .` + `vitest run`; Java — зелёным `./gradlew build`.
CI прогоняет то же самое: `.github/workflows/ci.yml`, три независимых
джабы — Rust, TypeScript, Java.

Сквозной тест против настоящей игры не входит в CI: он качает несколько
сотен мегабайт и требует настоящей видеокарты. Он включается вручную:

```bash
MINLAUNCHER_E2E=1 cargo test -p ml-desktop --test fabric_end_to_end -- --nocapture
```

Два других включаются так же — они качают настоящую 1.21.4 и настоящий
рантайм Java:

```bash
MINLAUNCHER_E2E=1 cargo test -p ml-desktop --test install_end_to_end -- --nocapture
MINLAUNCHER_E2E=1 cargo test -p ml-desktop --test runtime_end_to_end -- --nocapture
```
