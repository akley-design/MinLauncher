# Релиз

Документ описывает, как собирается и публикуется релиз MinLauncher:
что получается на выходе, где лежит ключ подписи, что должно совпадать
в номере версии и что делает CI.

---

## 1. Что выходит из сборки

Одна команда собирает всё:

```bash
npm run tauri:build
```

На выходе — три вещи:

| Файл | Что это |
|---|---|
| `bundle/nsis/MinLauncher_<версия>_x64-setup.exe` | установщик для пользователя (не требует прав администратора) |
| `bundle/msi/MinLauncher_<версия>_x64_en-US.msi` | установщик для корпоративных машин и развёртывания через GPO |
| `bundle/latest.json` | манифест автообновления |

Рядом с каждым установщиком лежит файл `.sig` — подпись его содержимого.
Без неё обновление не установится: обновлятор проверяет подпись публичным
ключом из `tauri.conf.json` и отказывается ставить файл, который не
проверен. Поэтому отсутствие `.sig` — ошибка сборки, а не предупреждение.

Каталог сборки лежит в `CARGO_TARGET_DIR` (по умолчанию — `target`),
то есть в `target/release/bundle`.

### Что лежит в установщике

Рядом с `minlaucher.exe` установщик кладёт ровно две вещи: сам исполняемый
файл и программу удаления.

`WebView2Loader.dll` в установщике нет, и он не нужен: загрузчик `WebView2`
в приложении линкуется статически, а сам движок на машине игрока ставит
отдельным пакетом (Microsoft Edge WebView2 Runtime), и Tauri при первом
запуске предлагает его поставить. Копия загрузчика, которую собирает
`crates/ml-desktop/build.rs`, нужна только тестам этого крейта: они лежат в
`target/debug/deps`, и туда её никто не кладёт — без неё тесты падают с
`STATUS_DLL_NOT_FOUND` ещё до первого теста.

Java-агента и мода в установщике нет. Оба собираются Gradle, и версия
мода привязана к версии игры: та, что собрана сейчас, сделана под 1.21.4 и
к текущему релизу 26.3 не подходит. Агент версии игры не требует, но без
него игра просто не измеряется изнутри — она запускается как обычно.
Лаунчер ищет агента рядом со своим исполняемым файлом, так что portable
сборка может положить его туда сама.

## 2. Номер версии: три места, одно число

Версия записана в трёх местах, и все три должны совпадать:

1. `Cargo.toml` → `[workspace.package] version` — оттуда берётся версия
   бинарника (`CARGO_PKG_VERSION`);
2. `crates/ml-desktop/tauri.conf.json` → `version` — оттуда берётся
   версия, которую показывает лаунчер;
3. тег релиза — `v<версия>`.

Почему это важно: обновление сравнивает версию **работающего** бинарника
с версией из манифеста. Если номер в манифесте окажется старше или
равен, игрок увидит «обновлений нет» — или, что хуже, получит откат на
старую сборку. CI проверяет совпадение всех трёх и останавливается с
понятным сообщением, если они разошлись.

Версия поднимается обычным коммитом, тег ставится на него:

```bash
# 1. поднять версию в Cargo.toml и в tauri.conf.json, закоммитить
# 2. опубликовать тег
git tag v0.2.0 && git push origin v0.2.0
```

## 3. Ключ подписи

Автообновление подписывается ключом в формате minisign.

**Приватный ключ не лежит в репозитории.** Он лежит у того, кто
выпускает релиз, и в CI попадает через секреты.

Сгенерировать новый ключ:

```bash
tauri signer generate -w ~/.tauri/minlaucher.key -p "<пароль>"
```

Команда печатает публичный ключ — его надо положить в
`crates/ml-desktop/tauri.conf.json` → `plugins.updater.pubkey`.
Приватный ключ и пароль — в секреты репозитория:

| Секрет | Что внутри |
|---|---|
| `TAURI_SIGNING_PRIVATE_KEY` | содержимое файла ключа (одна строка base64) |
| `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` | пароль ключа |

> Смена ключа ломает обновление у всех, кто стоит на прошлой версии:
> подпись новой сборки перестанет совпадать с публичным ключом в
> старом лаунчере. Менять ключ — значит выпустить версию, которая
> обновляется вручную, и только потом сменить публичный ключ.

## 4. Локальная сборка

```bash
npm ci
npm run tauri:build
```

Подпись на локальной машине необязательна: без ключа сборка пройдёт,
но файлов `.sig` не будет, и такой релиз публиковать нельзя. Чтобы
собрать с подписью:

```bash
export TAURI_SIGNING_PRIVATE_KEY="$HOME/.tauri/minlaucher.key"
export TAURI_SIGNING_PRIVATE_KEY_PASSWORD="<пароль>"
npm run tauri:build
```

Проверить, что установщик ставится:

```bash
# тихая установка в отдельный каталог
target/release/bundle/nsis/MinLauncher_<версия>_x64-setup.exe /S /D=C:\Users\Public\minlaucher-test
```

## 5. Публикация

Тег `v*` запускает `.github/workflows/release.yml`:

1. проверяет, что версии в `Cargo.toml`, `tauri.conf.json` и теге совпадают;
2. собирает установщики (`npm run tauri:build`) и подписывает их ключом из секретов;
3. собирает манифест `latest.json` скриптом `scripts/latest-json.mjs`;
4. публикует установщики, их подписи и `latest.json` в релизе GitHub.

Манифест нужен обновляющемуся лаунчеру: он спрашивает у endpoint
`https://github.com/minlaucher/minlaucher/releases/latest/download/latest.json`
и по нему узнаёт, что вышло, какой файл качать и какой подписью его
проверять.

Ключи в манифесте:

| Ключ | Для кого |
|---|---|
| `windows-x86_64-nsis` | клиент, установленный через NSIS |
| `windows-x86_64-msi` | клиент, установленный через MSI |
| `windows-x86_64` | клиент, который не различает виды установщика |

Обновляющийся лаунчер ищет сначала `{os}-{arch}-{вид}`, потом
`{os}-{arch}` — поэтому конкретный вид получает свой установщик, а
старые клиенты получают NSIS.

## 6. Что проверяется перед выпуском

- `cargo test --workspace --all-targets` — зелёное;
- `npm run test:run` и `npm run test:scripts` — зелёные;
- установщик ставится в чистый каталог и запускается;
- `latest.json` собирается из того, что реально попадёт в релиз
  (`scripts/latest-json.mjs` берёт подпись из файла `.sig` рядом с
  установщиком, а не пишет её руками);
- подпись проверяется тем же кодом, что проверяет её обновляющийся
  лаунчер: `minisign -p <публичный ключ> -V <файл>.sig`. У самой команды
  `tauri` подкоманды проверки нет — только `signer generate` и
  `tauri signer sign`.

### Подпись и версия

В доверенном комментарии подписи стоит версия релиза — её пишет сама
команда `tauri signer sign`. Обновляющийся лаунчер читает версию из
подписи и требует, чтобы она совпадала с версией манифеста
(`requireSignedVersion` в `tauri.conf.json`).

Зачем: ответ эндпоинта обновлений подписан не бывает, а подпись покрывает
только сам файл. Без этой проверки тот, кто отвечает на запрос эндпоинта,
может подставить в манифест новый номер версии вместе с файлом и подписью
старого релиза — и откатить игрока на настоящую, но устаревшую сборку.

Подпись, в которой нет версии, такую проверку не проходит. Поэтому
включать её можно только когда все релизы, с которых игрок ещё может
обновиться, подписаны версией: версия появилась в подписи начиная с
`tauri` 2.0, и наш первый релиз — 0.1.0 — уже подписан ей.

## 7. Инструменты сборки

Сборка идёт под MSVC (`stable-x86_64-pc-windows-msvc`): линкер и CRT
приходят из Visual Studio.

Build-скрипты и proc-макросы собираются под **хост**, а хост здесь — тот
же MSVC, поэтому `kernel32.lib` и `ucrt.lib` нужны и им. Ставить SDK
отдельно не нужно: его приносит компонент «Desktop development with C++»
Visual Studio Installer — единственное, что требует прав администратора
(1–2 ГБ).

Пути на этой машине нестандартные: SDK лежит внутри Visual Studio, а не в
`C:\Program Files (x86)\Windows Kits\10`, и переменные окружения собираются
вручную:

```bash
VS="/c/Program Files/Microsoft Visual Studio/2022/Community"
MSVC="$VS/VC/Tools/MSVC/14.44.35207"
SDK="$VS/SDK/ScopeCppSDK/vc15/SDK"

export PATH="$MSVC/bin/Hostx64/x64:$SDK/bin:$PATH"   # MSVC — первым
export LIB="$MSVC/lib/x64:$SDK/Lib"
export INCLUDE="$MSVC/include:$SDK/include/ucrt:$SDK/include/um:$SDK/include/shared"
```

Каталог MSVC в `PATH` идёт первым намеренно: в `PATH` есть `link.exe` от
Git, и если он попадёт раньше, линкером окажется не тот.

Каталог сборки тоже должен быть без кириллицы — это задано в
`.cargo/config.toml` (`target-dir`). Причина не в линкере: `rc.exe` пишет
пути иконки и манифеста в свой собственный файл и читает *его* через
кодовую страницу ANSI, так что путь внутри теряется по дороге. Линкер MSVC
с кириллицей работает, а вот ресурсы — нет.

Java-часть (агент и мод) собирается отдельно, Gradle, и в установщик не
входит: её требование — `GRADLE_USER_HOME` на пути без кириллицы, см.
`apps/java/gradle.properties`.
